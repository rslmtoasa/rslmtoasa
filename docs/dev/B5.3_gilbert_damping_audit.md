# B5.3 — Gilbert damping audit (report first)

**Milestone:** B5 (route-agnostic post-processing), task B5.3. **Branch:** `fable_v2`.
**Status:** audit complete; current driver and convergence evidence are recorded
in [VAL-08](VAL-08_DAMPING_INERTIA.md). This report remains the operator audit and

## The gate question

> Does the current Gilbert-damping implementation carry the **SOC-derivative
> torque operators**, or only the exchange-torque (Δ-splitting) flavor? If the
> SOC torque is missing, implementing it is a scope escalation Anders must approve.

## Finding 1 — the SOC torque operator IS present and correct (no escalation)

`exchange_dynamics.f90::calculate_gilbert_damping` builds the torque-correlation
damping and takes its torque matrices from
`hamiltonian::torque_operator_collinear` (`hamiltonian_build.f90:1041`), stored in
`hamiltonian%tmat(:,:,α,ntype)` for α = x,y,z. That routine builds the **spin-orbit
commutator torque**

  T^α = [σ^α, H_SOC],   H_SOC = ξ_ℓ **L·S**   (ℓ = p, d),

**not** the exchange-field (Δ σ) torque. Decisive check — expanding the code's Tx
blocks (lines 1071–1074), with `prefac = ½ ξ_ℓ` and the ×2 factors:

```
Tx_11 = +ξ i L_y     Tx_12 = -ξ L_z
Tx_21 = +ξ L_z       Tx_22 = -ξ i L_y
```

which is exactly `T^x = ξ (i L_y σ_z − i L_z σ_y) = [σ^x, ξ L·S]` (using
[σ^x,σ^y]=2iσ^z, [σ^x,σ^z]=−2iσ^y). Ty/Tz follow by cyclic permutation and match
lines 1076–1082. The SOC strengths `ξ_p = √(xi_p(1)·xi_p(2))`, `ξ_d =
√(xi_d(1)·xi_d(2))` are the **same** constants `build_lsham` uses for H_SOC itself
(`hamiltonian_build.f90:987`), so the torque is the genuine derivative of the SOC
Hamiltonian under a spin rotation.

This is physically the correct and complete torque for the Kamberský
torque-correlation Gilbert damping: in the adiabatic/equilibrium state the total
exchange+external effective field is parallel to **m**, so it contributes no
damping torque — the damping channel is SOC-mediated, and `T = [σ, H_SOC]` is
precisely it. **Conclusion: the SOC-derivative torque operator is present. No new
torque operators are needed; no scope escalation.**

Known limitation (pre-existing, not damping-specific): SOC is carried for p and d
only (f-orbital ξ = 0), identical to `build_lsham`. Out of scope for B5.3.

## Finding 2 — original wiring gap (resolved)

At the time of this audit, `calculate_gilbert_damping` and its companion
`calculate_moment_of_inertia` were public methods with zero call sites. The
current driver resolves that plumbing gap: `do_damping=T` invokes damping and
`do_inertia=T` invokes the explicitly experimental inertia diagnostic after the
same route-dispatched canonical Green functions are filled. The damping triad
and the convergence/limit checks are now recorded in VAL-08.

Good news for route-agnosticism: `calculate_gilbert_damping` consumes
`green%gij / green%gji` on the **energy grid**, evaluated at the Fermi point (it
does **not** use the `gij_eta` ladder, contrary to the B5 handover's assumption).
`green%gij` is filled route-agnostically by the existing `gf_route` dispatch in
`post_processing_exchange` (recursion / lehmann / dyson), exactly as J_ij is. The
current α triad therefore runs through the **same** machinery as the J_ij triad
— no separate eta-ladder plumbing, no consumer change.

## Consequence for the α triad (B5.3 remaining work)

α (the collinear Gilbert damping, the ½(α_xx+α_yy) diagonal average written to
`alldampings.out`) is a Fermi-surface quantity built from `green%gij`. Like J_ij it
is **broadening-defined** for a metal, so the recursion-vs-Lehmann comparison is an
**η-band extrapolated η → 0** (jointly with N_k → ∞ for the k-space routes), while
`lehmann ≡ dyson` stays the tight Σ=0 invariant — the same two-tier envelope
structure documented for J_ij/σ in `docs/dev/route_agnostic_estimators.md` (the α
section there is the reserved home for this η protocol).

## Historical re-land record (2026-07-16)

The following describes the earlier deferred attempt and is retained as history,
not as the current call-site state:

1. **`calculation%do_damping` flag** (Anders-approved wiring choice) invoking
   `calculate_gilbert_damping` in `post_processing_exchange` after the
   `gf_route`-dispatched `green%gij` fill; on-site α from the i==j pair. Plus a
   real fix to `calculate_gilbert_damping`: `spin_i` was an **uninitialized
   accumulator** (never zeroed before `spin_i = spin_i + …`; it enters the
   `1/spin_i` prefactor) — must be `spin_i = 0.0_rp` per pair.
2. **α triad measured** (bcc Fe, `xi_p/xi_d` SOC injected into the potential,
   12³ mesh, η=0.02, second-order H(k), on-site pair):

   | route | α = ½(α_xx+α_yy) |
   |---|---|
   | recursion | 0.0010541 |
   | lehmann   | 0.0026312 |
   | dyson     | 0.0026312 |

   Confirms the two-tier envelope: **`lehmann ≡ dyson` bit-identical** (Σ=0), and
   `recursion` vs `lehmann` a broadening η-band (ratio ≈ 2.5 here, like J_ij).
   α ≈ 1–3×10⁻³ is the physical bcc-Fe scale.

**Convention pins for the re-land:** SOC lives only in the on-site L·S block, so
(i) the potential must carry `xi_p/xi_d` (α ≡ 0 without them), and (ii) the k-space
routes need `kspace_ham_order='second'` (the only path that adds L·S to H(k)).

## Historical deferral reason

Adding the `do_damping` field to the `calculation` derived type perturbs memory
layout and **exposes a pre-existing latent uninitialized-variable bug in the B2
Lehmann first-order exchange path**: `J_ij` comes out `NaN` under the optimized
(`-O3`) build. It is a genuine heisenbug — **clean in every instrumented/debug
build** (`-finit-real=snan` runs clean, no FPE trap), the **recursion** path is
clean, and the **SOC / second-order Lehmann** path (the α triad above) is clean;
only the first-order Lehmann `J_ij` NaNs, and only for the memory layout the
`do_damping` field happens to produce. All `green` intersite arrays are zeroed at
allocation (`green.f90:285–321`), so the uninitialized value is a **local variable**
in the Lehmann exchange path (`fill_green_lehmann` / `calculate_exchange` /
`auxiliary_gij` / `predls`), not a `green` array.

The earlier `do_damping` attempt was split because that field exposed a latent
optimized-build Lehmann-exchange issue. The current Debug build and the VAL-08
campaign preserve the existing damping triad; this historical note does not
replace the current maturity limits in the Phase-II ledger.
